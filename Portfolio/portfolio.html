PROJECT 01 · PLANNING

기획 의도와 스토리

Exception은 프로그래밍 용어를 세계관과 전투 구조로 번역한 프로젝트입니다. 오류, 예외, 런타임, 데이터베이스 같은 추상적인 개념을 보스와 구역으로 바꾸고, 플레이어가 시스템을 복구한다는 목표를 액션 RPG의 전투 흐름으로 풀었습니다.

무대는 실행 흐름이 무너진 세계, The Runtime입니다. CMD, The First Command는 아직 완전한 root authority를 얻지 못했지만, Python과 Perl 구역의 보스들을 깨워 Runtime을 불안정하게 만들고 그 틈에서 root 권한을 빼앗으려 합니다.

플레이어 캐릭터 Hendel은 무너진 Runtime에 투입된 handler입니다. 조력자 Nel은 null의 의미를 가진 안내자로, 플레이어에게 직접적인 퀘스트 UI를 주지 않고 대화 속에서 작은 부탁들을 흘립니다. 이 부탁을 몰라도 게임은 정상 진행되지만, 모두 알아차리면 숨겨진 결말로 이어집니다.

메인 진행은 필드 → Python 보스 → 필드 → Perl 보스 → 필드 → CMD 최종전으로 구성했습니다. Python 보스 Vethara는 처리되지 않은 예외의 압박을, Perl 보스 Vritra는 낙타와 정규식 이미지를 섞은 변칙 패턴을 담당합니다. 보스전은 단순한 전투가 아니라 Runtime의 오류 구역을 하나씩 복구하는 과정입니다.

기본 엔딩은 CMD를 처치하고 Runtime을 안정화하는 구조입니다. 히든 엔딩에서는 Nel의 부탁을 모두 알아차린 플레이어가 Mimikatz, Authority Seized를 얻고, CMD가 거의 손에 넣은 root authority를 Hendel이 선점합니다. 이 선택으로 Hendel은 사라지지 않고 새로운 root가 되지만, CMD는 죽기 직전 handler로 위장한 바이러스를 남깁니다.

플레이어 공격 판정: Sweep과 인터페이스 기반 데미지 처리
PerformAttackTrace()
void AExceptionCharacter::PerformAttackTrace(float Damage, float GroggyDamage) {
    const FVector TraceStart = GetActorLocation() + FVector(0, 0, 45);
    const FVector TraceEnd = TraceStart + GetActorForwardVector() * AttackTraceDistance;

    TArray<FHitResult> Hits;
    FCollisionShape Shape = FCollisionShape::MakeSphere(AttackTraceRadius);
    bool bHit = World->SweepMultiByObjectType(
        Hits, TraceStart, TraceEnd, FQuat::Identity, ObjectParams, Shape, QueryParams);

    TSet<AActor*> DamagedActors;
    for (const FHitResult& Hit : Hits) {
        AActor* HitActor = Hit.GetActor();
        if (!HitActor || DamagedActors.Contains(HitActor)) continue;

        DamagedActors.Add(HitActor);
        if (HitActor->GetClass()->ImplementsInterface(UBRCombatInterface::StaticClass()))
            IBRCombatInterface::Execute_ReceiveCombatHit(HitActor, Damage, GroggyDamage, this);
    }
}
▸ 플레이 경험에서 해결한 문제

플레이어가 공격할 때 전방으로 구형 판정을 보내 맞은 대상을 찾는 코드입니다. 근접 액션에서 칼끝 판정이 너무 엄격하면 공격이 맞았다고 느낀 순간에도 빗나간 것처럼 보이기 때문에, 단순 LineTrace보다 넓은 판정을 사용했습니다.

▸ 구현 판단

같은 공격에서 한 Actor가 여러 충돌체로 여러 번 맞으면 데미지와 그로기 누적이 불안정해집니다. 그래서 TSet으로 중복 대상을 제거했고, UBRCombatInterface를 통해 보스, 파괴 오브젝트 등 대상별 처리를 분리했습니다.

PROJECT 01 · CORE CODE 02
HP, Stamina, Groggy를 한 컴포넌트에서 관리
BRStatComponent
bool UBRStatComponent::ApplyDamageToStats(float Damage, float GroggyDamage) {
    if (bIsDead || (Damage <= 0.0f && GroggyDamage <= 0.0f))
        return false;

    if (Damage > 0.0f) {
        CurrentHP = FMath::Max(0.0f, CurrentHP - Damage);
        BroadcastHP();
    }

    if (MaxGroggy > 0.0f && GroggyDamage > 0.0f && !bIsGroggy) {
        CurrentGroggy = FMath::Min(MaxGroggy, CurrentGroggy + GroggyDamage);
        BroadcastGroggy();

        if (CurrentGroggy >= MaxGroggy) {
            bIsGroggy = true;
            OnGroggy.Broadcast();
        }
    }

    if (Damage > 0.0f && CurrentHP <= 0.0f) {
        bIsDead = true;
        OnDead.Broadcast();
    }
    return true;
}
▸ 플레이 흐름에서 맡은 역할

보스와 전투 대상의 HP, Groggy, 사망 상태를 처리하는 공통 스탯 컴포넌트입니다. 데미지는 실패 압박을 만들고, Groggy Damage는 플레이어가 공격과 패링을 계속 시도할 이유를 만들어 줍니다.

▸ 실무형 구조로 분리한 이유

수치가 바뀔 때마다 BroadcastHP, BroadcastGroggy, OnDead 같은 이벤트를 내보냅니다. HUD는 이 이벤트를 받아 표시만 하므로, 전투 규칙을 고쳐도 UI 위젯 의존성이 같이 흔들리지 않습니다.

PROJECT 01 · CORE CODE 03
듀얼 보스가 동시에 공격하지 않도록 조율
BRBossTeamCoordinator
bool ABRBossTeamCoordinator::CanStartAttack(ABRBossBase* RequestingBoss) const {
    if (!RequestingBoss) return false;
    if (bAllowSimultaneousAttacks) return true;

    if (ActiveAttacker && ActiveAttacker != RequestingBoss)
        return false;

    const UWorld* World = GetWorld();
    return !World || World->GetTimeSeconds() - LastAttackFinishedTime >= TeamAttackGap;
}

bool ABRBossTeamCoordinator::NotifyAttackStarted(ABRBossBase* AttackingBoss) {
    if (!CanStartAttack(AttackingBoss)) return false;
    ActiveAttacker = AttackingBoss;
    RegisterBoss(AttackingBoss);
    return true;
}
▸ 난이도 감각에서 출발한 구조

듀얼 보스전에서 두 보스가 같은 순간 공격을 시작하지 못하게 조율하는 코드입니다. 현재 공격 중인 보스가 있으면 다른 보스의 공격 요청을 거절하고, 공격이 끝난 뒤에도 짧은 간격을 둡니다.

▸ 플레이 감각을 위한 코드

보스 두 마리가 동시에 공격하면 어렵다기보다 불공정하게 느껴질 수 있습니다. 그래서 난이도를 단순 수치가 아니라 공격권 관리로 조절했습니다. 이 구조 덕분에 보스 수가 늘어나도 같은 조율 방식을 재사용할 수 있습니다.

# 매 프레임 이미지 리사이즈 방지 (CPU 부하 및 드로우콜 최소화)
# 전역 캐시 딕셔너리를 활용한 메모리-연산 속도 교환 패턴
note_cache = {}

def get_note_image(size):
    # 해당 사이즈가 없으면 최초 1회만 연산 수행
    if size not in note_cache:
        # smoothscale: 안티앨리어싱 픽셀 보간 포함, 매우 무거운 연산
        note_cache[size] = pygame.transform\
            .smoothscale(NOTE_IMG, (size, size))

    # 이후 프레임부터는 메모리에서 즉시 반환 (Time Complexity: O(1))
    return note_cache[size]
▸ 문제 — 프로파일러로 특정한 78% CPU 점유

롱노트 20개 이상 구간에서 FPS가 60에서 18 미만으로 급락하는 프레임 스파이크가 발생했습니다. 프로파일러를 돌린 결과, 렌더 루프 내 pygame.transform.smoothscale이 매 프레임 반복 호출되며 전체 CPU 연산의 78%를 점유하고 있었습니다.

▸ 해결 — O(N) 연산을 O(1) 메모리 참조로 전환

size를 Key, 변환된 Image 객체를 Value로 하는 전역 해시맵 캐시를 도입했습니다. 최초 1회만 연산하고 이후에는 메모리에서 즉시 참조하도록 전환해 프레임 드랍을 완전히 제거했습니다. 시간 복잡도를 공간 복잡도로 교환하는 Space-Time Tradeoff의 실무적 효과를 직접 수치로 검증했습니다.

Object Pooling System (C++)
class BulletPool {
    // 연속된 메모리 공간 확보 → CPU 캐시 지역성(Cache Locality) 극대화
    std::vector<Bullet> pool;

public:
    // resize()로 런타임 힙 재할당 방지 (Pre-allocation)
    BulletPool(int size) { pool.resize(size); }

    Bullet* Acquire() {
        // 비활성 객체를 선형 탐색 (Cache Hit 보장)
        for (auto& b : pool) {
            if (!b.active) {
                b.active = true;
                return &b; // OS 시스템 콜 없이 포인터만 대여
            }
        }
        return nullptr; // 풀 오버플로우 방어
    }

    // 메모리 파괴 없이 논리적 비활성화 플래그만 변경
    void Release(Bullet* b) { b->active = false; }
};
▸ 문제 — 초당 300회 힙 할당으로 인한 프레임 히치

탄막 슈팅의 특성상 초당 수백 번의 new/delete가 반복되면 OS 메모리 요청 시스템 콜 오버헤드가 누적됩니다. 힙 파편화가 가중되며 보스 페이즈에서 16ms 이상의 프레임 히치가 반복 발생했습니다.

▸ 해결 — Pre-allocation과 Cache Locality 확보

게임 시작 시 std::vector에 최대 탄환 수를 일괄 선할당하고 상태 플래그만 토글하는 Object Pool을 설계했습니다. Linked List 대신 연속 메모리 구조를 선택해 CPU의 L1/L2 캐시 라인 프리패치를 활용했으며, 히치 현상이 완전히 사라졌습니다.

// 데미지 처리 인터페이스 — 개방-폐쇄 원칙(OCP) 달성
void AMyWeapon::ProcessHit(const FHitResult& Hit) {
    // 하드 캐스팅(Cast<T>) 없이 인터페이스 구현 여부만 검사
    if (Hit.GetActor() && Hit.GetActor()->Implements<UDamageableInterface>()) {
        // 무기는 피격 대상의 구체 클래스(Boss, Grunt 등)를 알 필요 없음
        IDamageableInterface::Execute_TakeDamage(Hit.GetActor(), DamageInfo);
    }
}

// 상태 변경 시 델리게이트 브로드캐스트 (Event-Driven)
void UHealthComponent::ApplyDamage(float Damage) {
    CurrentHealth = FMath::Clamp(CurrentHealth - Damage, 0.0f, MaxHealth);

    // UI와 강하게 결합하지 않고 이벤트만 송출
    OnHealthChanged.Broadcast(CurrentHealth, MaxHealth);
}
▸ 인터페이스를 통한 완전한 디커플링
